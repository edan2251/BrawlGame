# 04. 경기장

> **CR-001(2026-10-31)**: 경기에 쓰는 맵은 6절의 **맵 v2**(넓은 경기장, 테마, 광원, 구조물, 라운드마다 교체)로 바뀐다. 1~5절의 32 × 18 형식과 Box·Towers·Pit은 **v1 테스트 고정 자료**로 남는다(지우지 않음, 경기 순환에서는 뺌).

## 1. 원칙

- 경기장은 **한 화면에 전부 보이는** 가로 32 × 세로 18 유닛의 고정 공간이다. 카메라는 움직이지 않는다(연출용 흔들림과 짧은 확대만 허용).
- 지형은 위치 싸움을 만들기 위해 존재한다. 모든 맵은 벽, 발판, 구석 중 적어도 두 가지를 승부에 쓰이게 해야 한다.
- 경기장은 항상 벽으로 닫혀 있다. 떨어져 죽는 구멍은 없고, 대신 가시 같은 위험 지형이 있다.

## 2. 데이터 형식

맵은 사람이 읽고 고치기 쉬운 **문자 격자 텍스트**로 만든다. 파일은 `Assets/_Project/Data/Arenas/*.txt`.

```
name: Box
---
(32글자 × 18줄 격자)
```

| 문자 | 의미 | 칸 안에서 차지하는 부분 |
|---|---|---|
| `#` | 단단한 지형 | 칸 전체 (1 × 1) |
| `=` | 단방향 발판 | 칸의 위쪽 절반 (두께 0.5) |
| `B` | 튕김 패드 | 칸의 아래쪽 절반 |
| `^` | 가시(위험 지형) | 칸의 아래쪽 절반 |
| `1`, `2` | P1, P2 시작 위치 | 칸의 중심. 그 칸은 빈칸으로 취급 |
| `.` | 빈칸 | |

- 좌표계: 경기장 중심이 원점, x는 -16~16, y는 -9~9, 위쪽이 +y. 격자의 (열 c, 행 r) 칸은 `minX = c - 16`, `maxY = 9 - r`.
- 파서(`ArenaParser`)는 순수 C#이며 시뮬레이션 어셈블리에 둔다. 같은 종류의 인접한 칸을 탐욕적으로 합쳐 상자 목록으로 만든다(가로로 먼저 합치고, 같은 폭의 행끼리 세로로 합친다).
- 파서는 다음을 검증하고 실패하면 오류를 낸다: 32 × 18 크기, 테두리가 모두 `#`, 시작 위치가 각각 정확히 하나, 알 수 없는 문자 없음.
- 연출(`ArenaView`)은 같은 상자 목록으로 그림을 만든다. 시뮬레이션과 연출의 지형이 어긋날 수 없게 하기 위해서다.

## 3. 지형 종류의 동작

| 종류 | 동작 |
|---|---|
| 단단한 지형 | 모든 방향에서 막는다. 벽 미끄러짐, 벽 점프, 벽꽝의 대상 |
| 단방향 발판 | 위에서만 착지, 아래 + 점프로 통과(`02-movement.md`) |
| 튕김 패드 | 윗면에 닿으면 vy = 30. 공중 점프·대시 회복. 경직 중에 닿아도 튕긴다 |
| 가시 | 닿으면 데미지 15, vy = 20으로 튕겨 올림, 경직 20틱, 45틱 동안 가시 면역, 공중 점프·대시 회복(빠져나올 기회를 준다) |

## 5. 맵 검증 기준

- 세 맵 모두 파서 검증을 통과한다.
- 모든 맵에서 두 시작 위치 모두, 이동만으로 맵의 모든 발판에 도달할 수 있다. 수동 확인 대신 시나리오나 도달 가능성 테스트로 확인하는 방법은 자체 결정한다.
- Box의 가운데 기둥은 최대 점프로 넘을 수 있고, 짧은 점프로는 넘을 수 없다.
- Towers의 튕김 패드로 가운데 방에 들어갈 수 있다.
- Pit에서 가시에 떨어진 뒤 조작만으로 대지 위로 돌아올 수 있다.

## 6. 맵 v2 (CR-001, CP12부터)

### 경기장 크기와 카메라

- 가로 **36 × 세로 20 유닛 안팎**(D-023). 16:9 화면에 맞추는 정확한 값과 카메라 설정은 CP12의 자체 결정이다. 40 × 22.5보다 크거나 32 × 18보다 작아야 할 것 같으면 묻는다.
- 캐릭터 크기(1 유닛, 충돌 상자 0.9)는 그대로다.
- 카메라는 고정이다(연출용 흔들림과 짧은 확대만). 화면 끝까지 게임 화면이고, 경기장 테두리 벽은 일부가 화면 밖으로 나가도 된다(`08-visual-direction.md` 4절).
- 원칙은 1절과 같다: 항상 벽으로 닫혀 있고, 떨어져 죽는 구멍은 없다.

### 데이터 형식 v2

- **고정 지형**: 지금의 문자 격자(2절의 문자 그대로, 크기만 v2). 파서는 크기, 테두리, 시작 위치, 알 수 없는 문자에 더해 **좌우 대칭**을 검증한다.
- **짝 파일**(JSON 등, 형식은 자체 결정): 테마(`A` 민트, `B` 사이언, `C` 슬레이트, D-022), 주 광원 위치, 구조물 목록(CP13부터 채움, `09-props-physics.md` 5절).
- 시뮬레이션은 격자와 구조물만 쓴다. 테마와 광원은 연출만 쓴다.

### 라운드마다 맵 교체

- 경기 시드로 섞은 순서로 라운드마다 맵을 바꾼다. 6개를 다 쓰기 전에는 반복하지 않는다.
- 롤백 대상이므로 순서와 현재 맵은 시뮬레이션의 `MatchState`가 정한다(같은 시드면 같은 순서).
- F2는 디버그용으로 맵을 하나에 고정한다.

### 새 맵 6개 (테마당 2개)

이름과 배치는 CP12의 자체 결정이다. 원칙:

- 좌우 대칭.
- Rounds처럼 **화면 가득 구조물**(D-024). 빈 하늘이 넓은 맵을 만들지 않는다.
- 벽꽝이 날 수 있는 벽과 떠 있는 블록.
- 충전 돌진용 **긴 직선 통로**, 구석과 좁은 길.
- 가시를 쓰더라도 바닥 전체를 덮지 않는다(CP9 QA: 바닥 전체가 가시인 Pit은 지형 데미지의 57~70%가 가시였다).

### 검증 기준 (v2)

- 새 맵 6개가 파서 검증, 대칭 검사, 도달 가능성 탐색(5절, CP8 방식)을 통과한다.
- 같은 시드면 같은 맵 순서, 6라운드 안에 중복 없음, SyncTest 통과.
- 모드 A Smart 봇으로 맵마다 라운드 평균 10~30초.

### 구현 (CP12)

- 크기 36 × 20, 카메라는 세로 전체·좌우 벽 0.5 이상(S-107). 격자 `Data/Arenas/<이름>.txt` + 짝 파일 `<이름>.json` `{ "theme": "A", "light": [0, 25], "rotation": true, "props": [] }`(S-108).
- 맵: A Crossing·Foundry, B Gallery·Pillars, C Terrace·Vault(S-111). 순환은 `MatchState.Rotation`(S-109). F2와 Main 씬 설정은 S-110.
