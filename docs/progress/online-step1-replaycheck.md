## 3. 다른 PC 확인 대기

- 할 일: `Builds/ReplayCheck_pack.zip`을 다른 PC로 옮겨 풀고 `ReplayCheck.bat` 실행 → `results` 폴더를 압축해 가져오기(`README.txt`).
- 가져온 뒤: `results/run1·run2/result.txt`가 PASS인지, `trace.txt` 머리말의 CPU·OS. FAIL이면 그 틱 T로 이 PC에서 `-dumpticks T-1,T` 덤프를 뽑아 줄 비교 → 처음 다른 필드로 원인 계산을 찾는다. 고정소수점 전환은 그 근거가 있을 때 그 계산만 검토.
- 가능하면 CPU 제조사가 다른 PC(Intel)에서도 한 번.
- 기록 1개로 통과하면, 그다음에 기록을 늘린다(사람 플레이 기록, 다른 시드).

## 4. 후속 계획 (아직 착수하지 않음)

### 4.1 락스텝: 연결 검증과 전투 반응성 검증을 나눈다

| 검증 | 묻는 것 | 통과 기준 |
|---|---|---|
| 연결 검증 | 두 PC가 같은 입력을 같은 틱에 받아 같은 경기를 끝까지 계산하는가 | 확정 틱 체크섬 불일치 0, 입력 누락·중복으로 멈춘 틱 0(지연·손실 주입 포함), 이탈·시간 초과가 화면에 보임 |
| 전투 반응성 검증 | 입력 지연 D틱에서 주먹·박치기·받아내기·잡기가 손맛을 유지하는가 | 사람 판단(설문) + 측정: 누름 → 화면 반응 틱 수, 받아내기 성공률을 로컬(지연 0)과 비교. 기준값은 첫 측정 뒤 정함 |

연결 검증을 통과해도 반응성은 별개다. 반응성이 나쁘면 D를 줄일지, 롤백으로 갈지를 그때 정한다.

### 4.2 지연 수치의 기준

- 모든 지연 수치는 **왕복(RTT)** 으로 적는다. 앱이 중계를 거쳐 보낸 핑·퐁으로 잰다(ICMP 핑 아님). 편도는 RTT/2로 **추정**할 뿐 따로 재지 않는다.
- 락스텝 입력 지연 D(틱, 1틱 = 16.7 ms)는 편도 추정 + 흔들림 여유를 덮어야 멈추지 않는다. 예: RTT 100 ms → 편도 약 50 ms → D ≥ 3틱 + 여유 1~2틱(추정).
- 지연·손실 주입 수치(예: "RTT 100 ms, 손실 2%")도 왕복 기준으로 적고, 주입은 보내는 쪽 편도에 RTT/2씩 건다.

### 4.3 입력 누락·중복·순서·시간 초과

- 패킷마다 "상대가 아직 확인하지 않은 가장 오래된 틱부터 지금 틱까지"의 입력을 모두 다시 싣는다(중복 전송으로 손실 대비). 확인(ack) = 빈틈없이 받은 가장 큰 틱.
- 받은 입력은 틱 번호로 저장. 이미 있는 틱이 같은 값으로 다시 오면 버림(정상 중복). **다른 값**으로 오면 프로토콜 오류로 보고 경기를 멈춘다(덮어쓰지 않음).
- 순서가 바뀌어 와도 틱 번호로 제자리에 넣는다. 빈 틱이 메워질 때까지 그 뒤 틱은 계산하지 않는다(락스텝은 예측하지 않음).
- 상대 입력이 없어 다음 틱을 계산할 수 없으면 멈추고 "상대 기다리는 중"을 보인다. 입력이 없어도 100 ms마다 생존 신호. 5초 동안 아무것도 오지 않으면 "연결 끊김"으로 경기를 끝낸다(자동 재접속·이어 하기 없음, 첫 테스트 범위).
- 체크섬은 확정 틱만 몇 틱마다 교환. 불일치는 멈춤 + 양쪽 덤프·기록 저장(복구 아님).

### 4.4 자체 롤백은 작은 추가 작업이 아니다

기존 저장/복원과 SyncTest가 있어도 새로 필요한 것: 상대 입력 예측과 정정 시 되감아 여러 틱 재계산(한 프레임에 최대 N틱 Step, 성능 측정 필요), 두 PC의 시간 맞추기(한쪽이 앞서 달리지 않게), **연출 쪽 이벤트 정정**(되감기로 사라지거나 새로 생긴 타격 효과·소리·히트스탑·카메라 흔들림 처리, 지금 연출은 이벤트를 한 번만 받는다고 가정), 입력 기록·디버그 도구가 예측 틱을 다루게 하는 것. 규모는 락스텝 세션 층과 비슷하거나 더 클 수 있다(추정). 락스텝 반응성 측정 뒤에 정한다.

### 4.5 호스트 권위 방식 (우리 코드 기준)

| | 내용 |
|---|---|
| 얻는 것 | 다른 PC 결정론이 필요 없음(float 위험 사라짐), 동기화 어긋남이 원리상 없음, 4인·관전·중간 참가가 쉬움 |
| 비용 | 상태 전송: 전체 상태가 약 2200필드(덤프 기준) ≈ 9 KB(추정), 60 Hz면 초당 약 0.5 MB → 변경분 압축이나 낮은 전송률 + 보간을 새로 만들어야 함. 손님 PC의 자기 캐릭터 예측과 보정(사실상 롤백과 같은 되감기)이 없으면 손님 입력이 왕복만큼 늦음. 연출이 보간된 상태를 읽도록 바꿔야 함 |
| 위험 | 1대1에서 호스트만 지연 0(불공정), 타격 판정이 호스트 화면 기준이라 손님은 맞은 것을 늦게 봄, 호스트 PC가 나가면 경기 끝 |
| 판단 | 1단계에서 다른 PC 결정론이 깨지고 싸게 고칠 수 없으면 이 방식이 대안이 된다. 지금은 결정론 확인 결과를 먼저 본다 |
