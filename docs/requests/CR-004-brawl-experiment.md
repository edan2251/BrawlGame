# CR-004. 몸으로 싸우는 전투 실험 (`exp/brawl-v1`)

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-02 |
| 요청자 | 사용자 (기획 대화에서 정리) |
| 대상 브랜치 | 새로 만드는 `exp/brawl-v1`. `main`(= `cp-24`)은 얼린다 |
| 관계 | CR-003(폼·성장)의 코드와 문서는 **보존만** 하고 이 실험에서는 쓰지 않는다. CP 번호 대신 **단계 0, A, B, C, D/E, S**로 진행한다 |
| 멈추는 곳 | **단계 0의 질문 한 번**(백업 경로, 필요하면 판단이 애매한 파일 목록), 그리고 **A 끝, B 끝, C 끝**(플레이 확인). D/E는 C 피드백 뒤에 시작한다 |
| 읽는 범위 | 세션 시작 시 **0절, 3절, 현재 단계의 4절 행, 그 단계가 참조하는 규칙 절**(4절 아래 표)을 읽는다. 바뀌지 않은 나머지 절을 반복해서 읽지 않되, 현재 단계가 참조하는 절을 생략하지는 않는다 |

실험의 목적은 "이동, 주먹, 박치기, 그랩, 던지기 자체가 재미있는가"를 **적은 비용으로** 확인하는 것이다. 모든 수치와 규칙은 시험용 임시안이며, 확정이 아니다.

## 0. 진행 방식

### 0.1 멈춤과 재개
- **시작 전**: Unity MCP가 `Project_Brawl` 인스턴스를 가리키는지 확인한다(2절 1번).
- 단계 0(보존·분리) → A → (멈춤) → B → (멈춤) → C → (멈춤)의 순서다. 각 멈춤에서는 3.7의 형식으로 짧게 전달하고 사용자의 피드백을 기다린다.
- **캐릭터 외형 샘플(S)** 은 전투와 분리돼 있다. A~C의 대기 시간에 진행해도 되며, 전투 코드를 건드리지 않는다.
- D/E는 C 피드백을 받은 뒤 사용자가 시작을 알리면 진행한다.
- 세션이 끊겨도 한 줄로 이어갈 수 있게 `PROGRESS.md` 맨 위에 재개 방법을 적어 둔다. 사용자의 조치가 필요한 경우(사용 한도 소진, 에디터·MCP 단절)는 그 줄을 갱신하고 바로 알린다.

### 0.2 질문 정책
- **멈추고 묻는다**: 단계 0의 질문 한 번(백업 경로와 판단이 애매한 파일, 2절), 컴파일·테스트 오류가 두 번 시도 뒤에도 풀리지 않을 때, 결정론·저장/복원이 설계 변경 두 번 뒤에도 깨질 때, 9절의 "해당 단계 시작 전 결정"에 도달했는데 임시안을 쓰기 어려울 때, 느린 묶음 같은 오래 걸리는 검사를 돌려야 할 때(3.4).
- **묻지 않고 기록만 한다**: 수치 조정, 구현 방법, 임시안 안의 선택. 확정된 수치는 `DECISIONS.md`의 S에 한 줄씩 남긴다.

## 2. 보존과 분리 (단계 0)

사용자에게 묻는 것은 **한 번뿐**이다(4번의 백업 경로와, 2번에서 판단이 애매한 파일이 있을 때 그 목록). 승인 전에는 프로젝트 폴더 밖에 아무것도 쓰지 않는다.

1. **MCP 대상 확인**: 이 PC에는 다른 Unity 프로젝트의 인스턴스(예: `Cursor-Dash-master`)가 함께 연결될 수 있다. 시작 전에 연결된 인스턴스 목록에서 **`Project_Brawl`을 가리키는지** 확인한다. 다른 인스턴스이면 작업하지 않고 알린다. 이후 모든 MCP 호출에 `Project_Brawl`을 명시하고, `read_console`로 연결을 확인한다.
2. **읽기 전용 점검과 분류**(수정·삭제 금지): `git status`, `git log origin/main..HEAD`, `git branch`, `git tag`로 `cp-24` 이후의 변경과 미커밋·미추적 파일을 모으고, Git에 포함되지 않는 폴더(`Builds`, `Recordings`, `Replays`, `Logs`, `References`, `Captures`)의 존재와 크기, `Replays` 중 `Assets/_Project/Data/Scenarios` 안에 이미 옮겨 커밋된 것과 아닌 것도 함께 모은다. **파일(또는 폴더)마다 아래 분류와 처리 안을 적은 한 표로 보고**한다.

| 분류 | 예 | 처리 |
|---|---|---|
| 소스·문서의 의미 있는 변경 | `Assets/_Project`, `docs`, 의도한 `ProjectSettings`·`Packages` 변경 | 보존 대상(3번) |
| 이 요청서 | `docs/requests/CR-004-*.md`(미추적) | 변경분으로 세지 않는다. **`exp/brawl-v1`의 첫 커밋**으로 보존(7번) |
| 생성·캐시 파일 | `Library`, `Temp`, `Logs`, `obj`, 자동 생성 `*.csproj`·`*.sln`, `Captures`, `Builds`, `Recordings` | 커밋하지 않는다. 필요한 것은 백업만(5번) |
| 개인·민감 설정 | `.claude/`, MCP·API 키·토큰 파일, `.env`, `UserSettings/`, `.vscode`, `.idea` 등 | **커밋하지 않고 백업에도 복사하지 않는다.** 경로만 보고한다 |
| 판단이 애매한 것 | 위에 들어가지 않는 변경 | 커밋하지 않고 목록으로 질문(4번과 함께) |

3. **필요한 파일만 보존**: 소스·문서 분류에 해당하는 로컬 변경이 있으면, 파일을 **하나씩 경로로 지정해** `archive/cp24-local` 브랜치(`cp-24`에서 분기)에 커밋한다. `git add -A`와 `git add .`는 쓰지 않는다. 커밋 전에 스테이징 목록을 확인해 민감·생성 파일이 섞이지 않았는지 본다. 되돌리거나 지우지 않는다. 해당 변경이 없으면 이 단계는 건너뛴다. 애매한 파일은 4번의 답을 받은 뒤 같은 방식으로 처리한다.
4. **질문(한 번)**: 백업 폴더를 `D:\BrawlGame\Backups\CP24\`로 만들어도 되는지 묻고, 2번의 애매한 파일 목록이 있으면 함께 묻는다.
5. **백업**: `Builds`(CP24 빌드와 CP16 기준선), `References`, `Replays`, 필요한 `Logs`를 복사하고, `git bundle`로 전체 이력을 만든다. 2번 표의 민감 설정은 복사하지 않는다.
6. **백업 검증**: 파일 해시를 기록하고, 압축 해제를 확인하고, 백업된 빌드를 30초 실행해 로그를 확인하고, `git bundle verify`를 실행한다. 통과 결과를 `PROGRESS.md`에 짧게 남긴다.
7. **분리**: 검증이 통과하면 `archive/cp24`(= `cp-24`)와 `exp/brawl-v1`을 만들고, **이 요청서를 `exp/brawl-v1`의 첫 커밋으로 보존**한다. `main`과 `archive/*`에는 이 요청서를 커밋하지 않는다.
8. 이후 `git clean -x` 같은 Git 밖 파일을 지우는 명령은 쓰지 않는다.

**테스트 분리**: 옛 전투·성장에만 해당하는 테스트(폼, 전환, 선택·세트·증강, 투사체·반사, 에너지·가드·패링, 폼별 봇, 옛 입력 기록, 해당 맵의 도달성 탐색)는 `LegacyCombat` 카테고리를 붙여 제외한다. 삭제하지 않고, 깨져도 고치지 않는다. 분류가 애매한 클래스는 제외하지 말고 유지한다. 분류 목록은 로그에 한 번만 적는다. 이후 "빠른 묶음"은 `Slow`와 `LegacyCombat`을 모두 뺀 것이다.

## 3. 검증과 토큰 원칙

### 3.1 역할 분담

| 구분 | 내용 |
|---|---|
| **사용자가 확인** | 조작감, 재미, 전투 템포, 맵 밀도, 캐릭터 외형, 애니메이션, UI 가독성 |
| **Claude Code가 필수로** | 컴파일, 바꾼 기능에 직접 관련된 핵심 테스트, 공통 기반을 바꿨을 때의 안전 검사(3.3) |
| **기본적으로 하지 않음** | 3.5 |

사용자 확인 항목은 **조작법과 확인할 항목을 짧게 전달하고 피드백을 기다린다.** 직접 화면을 찍어 분석하지 않는다.

### 3.2 변경 유형별 검사

| 변경 유형 | 실행하는 검사 |
|---|---|
| 문서만 | 없음 |
| 외형·연출·UI·샘플(시뮬레이션을 건드리지 않음) | 컴파일, 에디터 콘솔 오류 확인 |
| 맵 데이터 | 컴파일, 해당 맵 하나의 파서·좌우 대칭·스폰 검사(기존 맵 테스트를 새 맵으로 필터) |
| 입력 형식·조준·입력 기록 | 컴파일, 3.3의 안전 검사 전부, 입력·기록 관련 테스트 |
| 시뮬레이션 상태·전투 규칙 | 컴파일, 바꾼 규칙의 테스트, 3.3의 안전 검사, 상태 필드 체크섬 범위 테스트 |
| 이동·충돌 | 컴파일, 이동·충돌·터널링 관련 테스트, 결정론 |
| 봇·샌드백(입력원) | 컴파일, 한 시드로 약 30초 분량의 시뮬레이션 틱을 돌려 불변식 위반이 없는지(실시간이 아니라 틱 진행) |

단순 외형 수정 때마다 전체 EditMode·PlayMode를 돌리지 않는다. 테스트는 클래스·이름 필터로 관련된 것만 실행한다.

### 3.3 공통 기반을 바꿨을 때의 안전 검사 (유지)

입력, 시뮬레이션 상태, 충돌을 바꿨다면 아래를 **기존 테스트 틀을 재사용해서** 실행한다.
- 같은 입력으로 두 번 실행해 체크섬이 같다(결정론).
- 저장 → 복원 → 재진행 결과가 같다.
- SyncTest(되감기 7틱)에서 불일치가 없다.
- 입력 기록 재생의 최종 체크섬이 기록과 같다.
- 새 상태 필드가 체크섬 범위에 모두 들어간다.

기존 테스트로 커버되지 않는 **핵심 규칙만** 새 테스트로 보완한다. 새 기능(조준, 탭/홀드, 그랩, 붙기) 상태가 들어간 시나리오에서 위 검사가 돌게 한다.

`InputFrame` 확장은 기존 생성자와 기록 읽기가 그대로 컴파일되도록 새 필드에 기본값을 두어 기존 테스트 수정을 최소화한다. 입력 기록 형식 버전은 올린다.

### 3.4 전체 회귀와 오래 걸리는 검사
- **전체 회귀**는 작은 수정마다 돌리지 않는다. **단계 끝에서 사용자에게 전달하기 직전 한 번**, 빠른 묶음(EditMode)을 실행한다. PlayMode는 그 단계 기능과 직접 관련된 것만 실행한다.
- **느린 묶음**(맵 도달성 탐색)은 맵·지형·이동·충돌 규칙을 바꾼 단계에서만 필요하다. **실행 전에** 필요성, 범위, 예상 시간을 한두 줄로 설명하고 사용자의 허락을 받은 뒤 실행한다. 새 맵 하나만 대상으로 줄일 수 있으면 그렇게 한다.

### 3.5 기본적으로 하지 않는 것
- 스크린샷·동영상 자동 촬영과 분석
- 여러 외형 후보의 반복 렌더링
- 장시간 봇 대전, 여러 시드의 대규모 밸런스 측정
- 반복적인 성능 측정(새 구조가 `Step` 핵심 경로를 바꿔 GC 할당이 의심될 때만 기존 할당 테스트를 한 번 실행)

**예외**: 사용자가 요청했거나 특정 오류를 해결하는 데 꼭 필요한 경우에만, 최소 범위로 진행하고 이유를 한 줄 기록한다.

### 3.6 빌드와 전달
- 작은 수정마다 Windows 빌드를 만들지 않는다. A~C의 전달은 **에디터에서 실행 가능한 상태**(씬 이름, 조작법, 재시작 키)로 한다. Windows 빌드는 사용자가 요청할 때만 만든다.
- 외형 샘플은 에디터 씬으로 전달한다. 포즈를 전환하는 간단한 UI를 두고, 사용자가 직접 본다.

### 3.7 읽기, 보고, 전달 형식
- 관련 파일과 바뀐 부분을 먼저 확인한다. 바뀌지 않은 긴 문서를 반복해서 전부 읽지 않는다.
- 성공한 테스트·측정의 로그 전체를 출력하지 않는다. 결과를 한 줄로 요약하고, 실패했을 때만 실패 항목의 로그를 확인한다. 긴 테스트는 한 번 시작하고 결과를 한 번에 읽는다.
- **단계 끝 전달 형식**(한 화면 분량): ① 실행 방법 ② 조작법 표 ③ 확인할 항목(5줄 이내) ④ 알려진 문제 ⑤ 검증 상태 표.

### 3.8 진행 기록
- 기록은 `PROGRESS.md` 한 곳에 한다. 단계마다 **변경 내용, 검사 결과, 미확인 사항, 다음 작업**만 최대 10줄로 적는다. CP 로그 파일을 따로 만들지 않는다.
- **새 명세 문서를 만들지 않는다.** 이 요청서가 명세이고, 확정된 수치는 `DECISIONS.md`의 S에 한 줄씩 남긴다. 같은 내용을 여러 문서에 길게 중복하지 않는다.
- `CLAUDE.md` 12절(토큰 절약 규칙)은 이 3절과 겹치는 내용을 합쳐 짧게 고친다(중복 금지, 이 브랜치 안에서만).

### 3.9 검증 상태 표기
각 검사는 **통과(확인 방법), 실패, 미실행, 사용자 확인 대기** 중 하나로 적는다. 실행하지 않은 검사를 통과로 표시하지 않는다.

### 3.10 핵심 오류를 방치하지 않는다
이 절약 원칙은 안전 검사를 면제하지 않는다. 컴파일 오류, 크래시, 결정론·저장/복원·입력 재생 불일치 같은 **핵심 오류**는 해결한다(두 번 시도 규칙). 확신이 없으면 가장 좁은 범위의 검사를 추가로 실행하고 이유를 기록한다.

## 5. 조작 규칙 (단계 B, C, 임시안)

### 5.1 탭/홀드: "선딜 겸용"

| 상황 | 규칙 |
|---|---|
| 좌클릭 누름 | 즉시 준비 동작(팔 당기기). 주먹 선딜(3틱)이 누름과 동시에 시작한다 |
| 임계 T 전에 뗌 | **주먹.** 타격 시점 = 뗀 시점과 선딜 끝 중 늦은 쪽. 탭 길이만큼만 늦다 |
| T까지 계속 누름 | 박치기 준비 완료(몸이 눌리고 색 신호). **충전은 T 이후부터 쌓인다** |
| T 이후 뗌 | **뗀 틱의 커서 방향**으로 발사. 충전 비율로 속도 18~34(현재 값) |
| 최대 충전 | 기존 값(24틱 유지) 뒤 자동 발사 |
| 주먹 후딜 중 눌림 | 6틱 동안 저장했다가 끝나면 시작한다(현재는 히트스탑 중에만 저장한다) |
| T의 값 | 초기 후보 **8틱**(약 0.13초). 조정값이다. 탭이 박치기로 오인되면 키우고, 박치기가 오래 눌러야 하는 느낌이면 줄인다 |
| 조준 | 커서 각도를 64방향으로 양자화해 입력에 담는다. 주먹은 뗀 틱의 방향을 쓴다 |
| 박치기가 벽에 닿음 | 임시로 종료(반사 없이 멈춤). B에서 느껴 보고 정한다. 표면 안쪽으로 겨눈 발사도 이 규칙을 따른다(7절) |

### 5.2 그랩과 잡은 상태의 우선순위

| 상황 | 규칙 |
|---|---|
| 우클릭 | 잡기 시작(선딜 5, 판정 3, 헛잡기 후딜 22: 현재 값) |
| 준비·충전 중 우클릭 | **준비·충전을 취소하고 잡기로 전환**(비용 없음). 받아내기는 타이밍이라 최우선이다 |
| 주먹·박치기·잡기 진행 중 | 우클릭 무시, 저장하지 않는다(타이밍 입력) |
| 잡은 상태(Holding) | **좌클릭을 누르는 순간** 커서 방향으로 던진다(탭/홀드 구분 없음). 이동은 느리게, 점프·주먹·박치기 불가 |
| 잡는 순간 이미 눌려 있던 좌클릭 | 무시한다. 뗐다가 다시 눌러야 던진다 |
| 최대 유지 | 초기값 **60틱**(약 1초) 뒤 커서 방향으로 자동 던진다. 현재 값 20틱은 8방향 입력용이라 마우스로 조준하고 클릭하기에는 짧다. 조정값이다. 잡은 동안에도 조준선을 표시해 던질 방향을 미리 보여 준다 |
| 받아내기 | 잡기 판정이 **박치기 중(Lunge 상태)인 상대**와 겹치면 잡기 성공, 박치기 종료. 같은 틱에 박치기의 타격과 겹치면 **잡기가 이긴다**(박치기 타격 무효). 위력 숫자 조건은 두지 않는다 |
| 잡힌 쪽(Held) | 조작 불가. 탈출은 9절에서 정한다 |

**받아내기에 위력 조건을 두지 않는 이유**: 6은 옛 위력 비교 규칙에서 "공격성 없는 접촉"을 걸러내던 값이다. 새 전투의 박치기는 최소 속도 18로 시작하고 속도가 떨어지면 끝나므로(명세 기준 12 미만), 박치기 중인 상대의 위력은 거의 항상 6을 넘는다. 조건이 실제로 걸리지 않으면서 설명하기 어려운 숫자만 남기므로 **상태(박치기 중)** 로 정의한다. 구현에서 박치기 종료 속도가 6 이상인지 확인하고, 아니면 이 판단을 다시 본다.

**벽꽝과 반복 방지(C)**: 던지기 기본 피해(고정)와 벽꽝 추가 피해(속도 비례, **상한**)를 분리한다. 던져지거나 벽꽝을 맞은 뒤 회복하고 나서 일정 시간은 잡을 수 없다(재그랩 보호). 거리가 멀수록 경직을 길게 만드는 방식은 쓰지 않고 피드백을 본 뒤 판단한다.

**충돌의 세 종류 구분**: 이동 접촉(착지, 벽 미끄러짐), 돌진 접촉(박치기가 지형에 닿음), **피격 충돌(맞거나 던져져 부딪힘 = 벽꽝)**. 붙기(D/E)는 앞의 둘에서만 일어나고, 피격 충돌은 붙지 않고 벽꽝으로 처리한다. 현재 코드의 `Hitstun`/`Thrown` 상태 판정을 그대로 쓴다.

**임시 상성 골격(확정 아님)**: 박치기가 주먹을 끊고(현재 규칙), 그랩이 박치기를 받아내고, 주먹은 선딜 중인 그랩을 맞힌다. C에서 이 골격이 "왜 이 동작을 고르는가"를 만드는지 본다.

## 7. 표면 이동 (단계 D/E, 실험 기능)

방향은 **눌린 A/D 집합이 바뀔 때만** 현재 표면의 매핑으로 정하고, 그 외에는 유지한다. W는 쓰지 않는다.

**새로 누를 때의 매핑**

| 표면 | D | A |
|---|---|---|
| 바닥 | 화면 오른쪽 | 화면 왼쪽 |
| 천장 | 화면 오른쪽 | 화면 왼쪽 |
| 오른쪽 벽 | 위 | 아래 |
| 왼쪽 벽 | 위 | 아래 |

흐름 예: D를 계속 누르면 바닥 → 오른쪽 벽 위 → 천장 왼쪽 → 왼쪽 벽 아래 → 바닥. A를 계속 누르면 바닥 → 왼쪽 벽 위 → 천장 오른쪽 → 오른쪽 벽 아래 → 바닥.

**규칙**

| 상황 | 임시 규칙 |
|---|---|
| 모서리(외곽 프레임의 오목 모서리) | 방향 유지, 표면만 전환(집합이 안 바뀌어 재결정 없음) |
| 공격·잡기 때문에 잠시 멈춤 | 키를 누르고 있으면 방향 기억 유지. 행동이 끝났을 때 붙어 있고 키가 눌려 있으면 같은 방향으로 재개 |
| 키를 실제로 뗌(A/D 둘 다) | 정지하고 방향 기억 삭제. 다시 누르면 새로 결정 |
| D를 누른 채 A 추가(양쪽 동시) | 중립으로 정지(기존 이동과 같음). 기억은 유지 |
| 그 상태에서 한쪽만 뗌 | 남은 키로 현재 표면 기준 재결정 |
| 점프 | 표면 바깥으로 떨어지고 기억 삭제. 공중 A/D는 화면 좌우. 다시 붙을 때 키가 눌려 있으면 "새로 누름"으로 처리 |
| 박치기 발사 | 표면에서 떨어지고 기억 삭제. 붙을 때는 점프와 같음 |
| 피격·던져짐 | 떨어지고 기억 삭제. 회복 뒤 키가 눌려 있어도 새로 누른 것으로 처리 |
| 잡은 쪽 / 잡힌 쪽 | 잡은 쪽은 멈춤(기억 유지), 잡힌 쪽은 떨어지고 기억 삭제 |
| 붙기 조건 | 외곽 벽·천장과 **내부 사각 지형의 옆면·아랫면**에 이동·돌진 접촉으로 닿으면 자동으로 붙음. 윗면(바닥 포함)은 기존 서기. 피격 충돌은 붙지 않음 |
| 떼기 | 점프, 박치기, 또는 S(놓고 떨어짐) |
| 표면 안쪽으로 겨눈 박치기 | **조준을 바꾸지 않고 그대로 발사한다.** 발사 직후 같은 표면에 닿으면 5.1의 "벽에 닿음" 규칙(임시: 종료)이 처리하고, 이어서 붙기 조건에 따라 다시 붙는다. 안쪽 조준을 막거나 평행 방향으로 바꾸는 별도 보정은 두지 않는다 |
| 내부 지형 | 윗면은 기존 서기. **옆면·아랫면은 D/E 모두 붙을 수 있다. 달리기는 외곽(사방 프레임)에서만 한다.** 내부 지형에 붙은 상태의 A/D는 D·E 모두 무시하고, 내부 지형의 모서리 전환도 없다 |
| 달리기 속도 | 바닥 달리기와 같게 시작(박치기보다 훨씬 느려 추격 가능) |

**비교안**: **D** = 외곽·내부 지형에 붙고 정지한 채 유지하다 뛰어들기(A/D는 표면에서 무시). **E** = D + 위 표의 **외곽** 표면 달리기(내부 지형은 달리기 없음). 같은 맵·전투·봇에서 스위치 하나로 전환한다. 중력은 항상 아래이고, 붙은 동안만 꺼진다.

## 8. 캐릭터 외형 샘플 (단계 S)

**목표**: 휴먼 폴 플랫풍의 통통한 인형. 둥근 머리, 살집 있는 몸통, 두꺼운 팔다리, 뭉툭한 손발, 관절이 이어지는 겉살, 흐느적거리지만 주먹 방향과 타격은 명확한 모습이다. 슬라임처럼 전부 녹아 붙는 느낌이나 사각 몸통에 굵은 막대 팔다리만 붙인 정도는 목표가 아니다. 기존 IK(`TwoBoneIK`, `LimbRig`)를 재사용한다.

| 후보 | 방식 | 자동화 |
|---|---|---|
| **R1 부위 메시 + 관절 구** | 머리·몸통·팔·다리를 따로 만든 둥근 부위로 겹치고 관절에 둥근 덩어리를 둠 | 코드만 |
| **R2 IK 체인 튜브** | 관절을 따라 굵기가 변하는 매끈한 튜브 메시를 매 프레임 생성, 몸통은 스프링 메시 | 코드만 |
| R3 SDF 합치기 | 부위를 셰이더 한 번에 매끄럽게 합침. 슬라임식 융합과 팔 겹침 구분이 위험 | 셰이더 작업 |
| R4 2D 스키닝 | Unity 2D Animation. 스크립트로 뼈·메시 생성이 가능한지 이 프로젝트 버전에서 확인이 필요 | 미확인 |

**진행**
- **S1**: R1과 R2를 한 씬에 하나씩 둔다. 포즈 전환 UI로 달리기, 위·아래·대각선 주먹, 천장 자세, 박치기, 잡힘, 던져짐을 볼 수 있게 한다. 판정 상자와 주먹 판정 원을 겹쳐 그리는 오버레이를 켜고 끌 수 있게 한다. **S1 전달 때 R3/R4 비교를 진행할지 한 줄로 묻는다**(S1로 충분하면 건너뛴다).
- **S2**(사용자가 원할 때만): R3 샘플 하나와 **R4 자동화 가능성 확인**(작은 스프라이트 하나, 뼈 3개). R4는 자동 생성 가능 여부, 사람이 손으로 해야 하는 단계 수, 결과 품질, 실행 비용을 **텍스트 표로만** 보고한다(스크린샷 촬영 없음).

**확인할 것(사용자가 직접)**: 팔이 몸통 앞을 지나거나 양팔이 겹칠 때 구분되는지, 외형과 판정의 괴리. 외형 기준은 임시로, **보이는 몸통 폭이 판정 폭(0.9) 이상 ×1.25 이하**이고 주먹 끝이 주먹 판정 원 안에 있는 것이다. 판정이 보이는 몸보다 크면 안 된다.

## 9. 아직 결정이 필요한 규칙

| 시점 | 결정 | 임시안 |
|---|---|---|
| **C 전** | 잡기 유지·탈출 방식 | 시간 제한(초기값 60틱, 5.2) + 자동 던짐만(탈출 없음) |
| **C 전** | 받아내기 성공 시 박치기의 운동량 | 잡은 쪽 제자리, 잡힌 쪽 속도 0 |
| **C 전** | 재그랩 보호 방식 | 던져진 뒤 회복한 다음 일정 시간 잡기 불가 + 벽꽝 추가 피해 상한 |
| **D 전** | 붙기를 자동으로 할지 키로 할지 | 외곽 벽·천장과 내부 지형 옆면·아랫면 자동 |
| **D 전** | 떼기 키 | S |
| B 중 튜닝 | T 값, 벽에 닿은 박치기 처리(얕은 각도로 바닥·표면에 닿을 때 포함) | 8틱, 종료 |
| 기본값 | 라운드 선승 수, 샌드백 동작 | 3선승, 체력 표시 + KO 시 리셋 |
